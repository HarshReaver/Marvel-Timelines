Chapter 1The whole map on one page

It started as one X-Men timeline chart. It grew into nine pages covering 169 Marvel films, series and cartoons, a domain of its own, visitor stats, and search listings. Here is every moving part and how they connect. The rest of this guide zooms into one part at a time.

The one-line summary. It's a static site: plain files with no server program and no database. GitHub stores and serves the files, BigRock points your name at GitHub, and the visitor's own browser does the work of building each page.

Chapter 2Building the pages

WEB DEVLLD

Typing 169 titles into nine HTML pages by hand would mean fixing every typo in many places. So the titles live in one data file, and small scripts turn that data into trees, cards and pop-ups inside the visitor's browser. Change one line of data, and every page that shows that title updates.

Chapter 3Shipping changes safely

DEVOPS

Hundreds of changes went live during this project, and the site was never left broken. That came from a fixed routine: test on your own computer, push, let GitHub deploy, then check. DevOps is exactly this: getting changes from a laptop to real users quickly without breaking things.

The tools in that pipeline

StepToolWhat to know
Test locallypython -m http.server 8765 in the project folderThen open http://localhost:8765. Press F12 → Console for errors, and the phone icon for phone width.
Version controlgit, via GitHub DesktopA commit is a saved snapshot with a message. Push uploads it. Fetch/Pull brings down changes made on GitHub (like the CNAME file GitHub created).
CI/CDGitHub Actions: "pages build and deployment"Runs by itself on every push to main. You can watch it in the repo's Actions tab. Once it failed with a GitHub server error (500); re-running fixed it.
Cache busting?v=14 on every asset linkBrowsers keep old copies of CSS/JS. Raising the number makes it a new address, so everyone gets the fresh file at once.
Build stepnode tools/build-seo.mjsGenerates the SEO parts from data. Safe to rerun; it replaces its own block instead of adding another.
Order matters. The domain switch was done so nothing ever pointed at an address that didn't work yet: DNS record first, wait until it resolved, then the GitHub custom domain, then HTTPS, then new links. GoatCounter counted both addresses during the switch, so no visits were lost.

Chapter 4Giving it a name

NETWORKINGDEVOPS

The site first lived at harshreaver.github.io/Marvel-Timelines. That's long, and the address you shared on WhatsApp. You already owned harver.in at BigRock, so the site moved to marvel.harver.in, a subdomain that costs nothing extra. Old links still work: GitHub forwards them.

What happens when someone types marvel.harver.in

Records, explained

RecordMeansUsed for
CNAME marvel → harshreaver.github.io"This name is a nickname for that name"Subdomains like marvel.harver.in. This is what you have.
A @ → 185.199.108.153 (×4)"This name lives at this IP address"A bare domain like harver.info, if you ever host one on GitHub (plus a CNAME for www).

Setting it up again (step by step)

  1. BigRock: Orders → harver.in → DNS Records → CNAME tab → Add CNAME Record. Name marvel, value harshreaver.github.io, save.
  2. Check: in Command Prompt run nslookup marvel.harver.in 8.8.8.8. When it mentions github.io or 185.199…, it's live.
  3. GitHub: repo → Settings → Pages → Custom domain → marvel.harver.in → Save. GitHub adds a CNAME file to the repo. Pull it in GitHub Desktop, and never delete it.
  4. HTTPS: wait until "Enforce HTTPS" can be ticked (minutes to an hour), then tick it.

Chapter 5Locking the door

SECURITY

A site with no server and no database has very little to attack: there's no login to break into and no data to steal. Security work here was about the connection, the domain, and what other people's code can do on your pages.

TopicWhat's in placeWhy it matters
HTTPS (TLS)Let's Encrypt certificate, "Enforce HTTPS" tickedEncrypts traffic and proves the site is really yours. http:// is forced to https://.
Subdomain takeoverCNAME record at BigRock + CNAME file on GitHubIf you ever delete the GitHub site or its custom domain, also delete the CNAME record at BigRock. A record that points at an unclaimed github.io site lets a stranger claim marvel.harver.in and show anything on it.
Third-party scriptsOnly GoatCounter; images from Wikipedia/WikimediaAny script you load can do anything on your pages, so keep the list short and trusted.
SecretsNone in the repoThe repo is public. Never commit passwords, API keys or tokens; anyone can read them, and bots scan GitHub for them.
PrivacyGoatCounter is cookieless; nothing personal storedNo cookie banner needed. Dark mode and section choices stay in the visitor's own browser.
Security headersNot possible on GitHub PagesSEO tools flag missing HSTS, CSP and X-Content-Type-Options. GitHub Pages doesn't let you set server headers, and with no logins or forms the risk is low. A host like Cloudflare Pages or Netlify would allow them.
Email on a public pageAddress put together by app.jsBots scan web pages for email addresses to spam. The address isn't written in the HTML; the script joins its two halves when the page loads, and most bots don't run scripts. It's also kept out of the README, because GitHub is scanned heavily.
Verification filegoogle1b416379081362bb.htmlProves to Google you own the site. Harmless to keep public; deleting it loses Search Console access.

Chapter 6Why it's built this way

HLD

High-level design (HLD) is the view from above: which big pieces exist, how they talk, and why this shape was chosen over others. In interviews you'd be asked "design X", and you'd answer with a diagram like this, plus trade-offs.

The trade-offs

What this design wins
  • Cost: free hosting, free HTTPS; only the domain costs money.
  • Scale: a viral Reddit post is fine. GitHub's CDN serves the same files to everyone; there's no server to overload.
  • Speed: files come from a nearby server; Rank Math measured 0.05–0.8 s responses.
  • Security: no login, database or server code means very little to attack.
  • Simplicity: deploying is just a push. Rolling back is a revert.
What it gives up
  • No accounts or saved data across devices (watch lists would need a backend).
  • Crawlers that skip JavaScript see less, which is why the plain lists and build script exist.
  • No control over server headers (Chapter 5).
  • Depends on GitHub: if Pages is down, so is the site. Limits: about 1 GB site size and 100 GB traffic a month, far above what you need.
If it ever needs more. The usual next step is a small backend (for example Cloudflare Workers or Supabase) only for the parts that need it, such as user watch lists, while the pages stay static. That pattern is called Jamstack.

Chapter 7Getting found

SEOWEB DEV

Chapter 8Watching who comes

DEVOPSSEO

The site was shared on WhatsApp before stats were set up, so the first visits were only partly counted. Two dashboards now answer the two big questions: "who visited?" and "how did Google show us?"

GoatCounter: marvel-timelines.goatcounter.com
  • Page views, countries, devices, where people came from.
  • Unique visitors: the dashboard counts people, not every page load. For exact numbers, Settings → Export gives a CSV with a Session column (one per visitor).
  • Its history can't be moved into Google Analytics: GA4 only accepts visits from the last few days, and it would need a cookie banner.
  • Loaded by app.js only on the real addresses, so your local tests don't count.
  • Ad blockers hide some visits, so real numbers are a bit higher.
Google Search Console: property https://marvel.harver.in/
  • What people searched to find you, clicks, and which pages are indexed.
  • Sitemap submitted; "Couldn't fetch" at first is normal.
  • URL Inspection → Request indexing (about 10 a day).
Reading odd visits. Visits from the US or Belarus before anyone in those places knew about the site are usually bots (certificate-log scanners, SEO checkers, Google's own tester), or people on a VPN. Bot clues: Linux or headless Chrome, desktop screen sizes, one page, and a time matching when a checker ran. Your real audience so far is Android phones in India. In engineering this is called observability: being able to tell what's happening from the outside.

Chapter 9Bugs we hit and what they taught

WEB DEVDEVOPS

Every real project has bugs. What matters is finding the cause, not just hiding the symptom. These are the ones worth remembering, written the way engineers write a short post-mortem.

The old link that kept coming back

Symptom The footer still showed the old "Marvel-Timeline" link after it was fixed, and it led to a 404.

Cause Browsers kept the old app.js in their cache.

Fix ?v= version tags on every asset.

Lesson Caching makes sites fast, so plan how to invalidate it.

The countdown that said "1 days"

Symptom Wrong wording, and no plan for after release.

Cause Time-of-day maths and a single hard-coded film.

Fix Whole calendar days in UTC, plural rules, and a list of films with "out" and "gone" dates.

Lesson Dates and time zones are a classic source of bugs. Test the edge days.

A duplicate SEO block

Symptom Running the build script twice doubled the tags.

Cause The clean-up search didn't match its own comment.

Fix Match everything from seo:start to seo:end, all occurrences.

Lesson Make scripts idempotent: running them twice gives the same result as once.

The About page with 143 items

Symptom A page meant to list nothing listed every title.

Cause In JavaScript an empty list [] counts as "true".

Fix Return false instead.

Lesson Know your language's truthy and falsy rules.

Invalid structured data

Symptom Semrush flagged 4 invalid items.

Cause Two specials were marked "Movie" but carried episode counts.

Fix Only TV series get seasons and episodes.

Lesson Validate generated data against its schema (validator.schema.org).

The deploy that failed for no reason

Symptom A push didn't go live.

Cause GitHub's own server error (500), not your files.

Fix Re-run, or push again.

Lesson Read the log before changing code. Not every failure is yours.

Borders cut off at 100% zoom

Symptom The top line of the section buttons vanished after the bar slid back.

Cause A CSS transform left the bar on half pixels, and the scrolling row clipped the border.

Fix Spare padding, and hiding the bar by moving its sticky position in whole pixels.

Lesson Bugs that show at only one zoom level are usually sub-pixel rounding.

Unreadable and mismatched colours

Symptom Mixed-colour section buttons; dark text on dark red; a white logo strip over the posters.

Cause Colours chosen per section, not per page theme.

Fix One page colour for all buttons, the strip removed (logos stay in the footer).

Lesson Users notice consistency. Check contrast in both themes.

Chapter 10Everyday tasks, step by step

Add a new film or series

  1. Open assets/data.js. The comment at the top explains every field. Copy a similar title's entry and change it. Entries are in release order.
  2. If it's not out yet, add up:1,rel:"2027-05-07" (its release date). It drops the Upcoming tag on that day by itself. For an MCU title, also give it so: (its place in story order).
  3. Poster: add an entry to assets/media.js with the Wikipedia image, or save a poster about 400px wide into assets/posters/ and use "img":"assets/posters/name.jpg","w":400,"h":600.
  4. If it belongs at a particular point in a story tree (X-Men forks, Spider-Verse lanes), it may also need adding to that page's SPECS in assets/tree.js.
  5. Run node tools/build-seo.mjs (VS Code: Terminal → New Terminal).
  6. Raise the version numbers (data.js?v=, media.js?v=) in all pages: Ctrl+Shift+H in VS Code replaces them everywhere.
  7. Test locally, then commit and push.

Fix the character filter

If a title is missing from a character, or listed under the wrong one, open the CHARACTERS list at the bottom of assets/data.js. Add the title's id to that character's add:[…] list (missing) or not:[…] list (wrong). To add a new character, copy a line and change the name and pattern. Then raise data.js?v= in all pages.

Change the contact links

They're the REPO_URL, LINKEDIN, INSTAGRAM and EMAIL lines near the top of assets/app.js. Raise app.js?v= after changing.

After you watch Doomsday

Rewrite its d:"…" summary in data.js (it still describes the trailer and cast), then do steps 5 to 7 above.

Change the countdown

Edit the FILMS list at the top of assets/home.js: out is the release date, gone is when it hands over to the next film. Raise home.js?v= in index.html.

Change a page's colours

Each page's colours are one line near the top of assets/style.css, for example [data-theme=tva]{--bg:…;--accent:…}. Section button colours are the .t-jump{--jump:…} lines. Raise style.css?v= after changing.

Change a search title or description

Edit the PAGES list near the top of tools/build-seo.mjs, then run it. Keep titles under 60 characters and descriptions under 155.

Chapter 11Getting traffic

Nobody can promise a top Google spot or that Google's AI will recommend a site. The technical side is done. What decides it from here is other sites linking to yours, people clicking and staying, and time: a few weeks to appear for the site's own name, months for busy searches like "MCU watch order".

  1. Request indexing for the main pages in Search Console (Chapter 8).
  2. Bing Webmaster Tools (bing.com/webmasters): choose "Import from Google Search Console". Bing's index feeds ChatGPT search, Copilot and DuckDuckGo.
  3. Link from places you control: LinkedIn (Featured, plus a short post about building it), the Website field on the GitHub repo, your GitHub profile README, harver.in.
  4. Answer where fans ask "what order should I watch": Reddit (r/MCU, r/marvelstudios, r/xmen; read each subreddit's self-promotion rules first), Quora, a Letterboxd list. One good thread can beat months of search traffic, and each link raises your authority score.
  5. Stay fresh around releases: Doomsday (18 December 2026), Beyond the Spider-Verse (June 2027), Secret Wars (December 2027). Update summaries soon after each.
  6. Watch what works: GoatCounter for pages and sources, Search Console's Performance report for searches. Strengthen the pages that already get found.
